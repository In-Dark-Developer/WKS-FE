# ADR-20260923: 요구사항 Notion DB 를 ⚔️ PRD 하나로 모으고, 열의 소유자를 나눈다

- Status: Accepted
- Date: 2026-09-23
- Deciders: @jjjung0921

## Context

요구사항이 세 곳에 있었다 — 저장소 `docs/prd/`(원문), 🙋 요구사항 색인 DB(CI 가 만든 읽기 전용 미러,
ADR-20260913-notion-index-sync), 그리고 2026-09-23 에 팀 워크스페이스에 새로 만든 ⚔️ PRD DB(담당·상태·
FE/BE 를 붙인 추적 보드). 뒤 둘은 ID 체계도 다르다(색인은 FR-1…, 보드는 FR-11·FR-21… 그룹 번호).
같은 요구가 두 ID 로 불리면 Task·PR 에서 무엇을 가리키는지 흐려진다.

## Problem

Notion DB 를 하나로 줄인다면 어느 것을 남기고, 요구 원문과 작업 추적 중 무엇을 어느 쪽이 소유하는가.

## Alternatives

1. 색인 DB 유지, 보드 폐기 — CI 를 안 고쳐도 된다 / 담당·상태·FE/BE 를 적을 곳이 없어 보드를 다시 만들게 된다.
2. 보드 하나로 모으고 CI 를 그쪽으로 돌린다 — DB 가 하나다 / 스크립트의 속성 매핑을 고쳐야 한다.
3. Notion 을 원천으로 삼고 `docs/prd/` 를 CI 가 생성한다 — 기획이 Notion 에서 바로 고칠 수 있다 /
   요구 변경이 PR·리뷰 없이 들어오고(AGENTS Rule 7 Spec first 가 무너진다), CI 가 보호 브랜치에 봇 커밋을
   해야 하며, 표로 표현되지 않는 절(화면 흐름·제약·미해결 질문)은 생성할 수 없다.

## Decision

2안. Notion 요구사항 DB 는 **⚔️ PRD**(`3dffb10f-6501-80c9-90c3-000b0186adcf`) 하나만 쓴다. 🙋 요구사항 색인
DB 는 더 이상 쓰지 않는다(ADR-20260913-notion-index-sync 의 PRD 절을 대체한다 — ADR·Phase 색인은 그대로다).

열의 소유자를 나눈다.

| 열 | 소유 | 채우는 주체 |
|---|---|---|
| `ID` · `이름`(요구 원문) · `구분` · `우선순위` | 저장소 `docs/prd/` | CI 가 push 마다 ID 로 upsert |
| `상태` · `담당자` · `FE` · `BE` · `수용 기준` · `비고` | Notion | 사람이 보드에서 관리 — CI 는 쓰지 않는다 |

`구분`(도메인)을 CI 가 채울 수 있도록 FR 표에 `Area` 열을 둔다. NFR 은 모두 `비기능` 이다.
우선순위는 저장소 표기(Must/Should/Could)를 보드 표기(P0/P1/P2)로 옮겨 적는다.

## Rationale

- 요구 원문이 git 에 있으면 변경이 PR 로 오고 리뷰·이력이 남는다. 구현 PR 이 근거로 삼을 커밋이 생긴다.
- 추적 열은 시시각각 바뀌고 리뷰할 것이 아니다. Notion 이 잘하는 일이라 그대로 둔다.
- CI 가 추적 열을 건드리지 않으므로 사람이 보드에서 적은 담당·상태가 동기화에 지워지지 않는다. 이전 구현은
  Phase 에서 계산한 `상태` 를 덮어썼다 — 보드로 옮기면서 그 동작을 없앴다.
- 3안은 기획이 Notion 에서 요구를 직접 쓰는 팀에 맞다. 이 팀은 기능명세서 DB 가 기획 소유이고 PRD 는
  개발이 쓰므로 해당하지 않는다. 뒤집을 일이 생기면 이 ADR 을 대체한다.

## Consequences

- 긍정: 요구 ID 가 한 벌이다. 보드의 담당·상태가 안전하다. Notion 에 사람이 적을 자리가 남는다.
- 부정 / 감수한 것: FR 표에 열이 하나 늘었다. 기획이 요구 문구를 고치려면 PR 을 거쳐야 한다.
- 후속 작업: ⚔️ PRD 의 기존 행(2026-09-23 수기 생성분)을 지우고 CI 가 저장소 번호로 다시 만들게 한다.
  🙋 색인 DB 는 보관만 하고 갱신하지 않는다.
