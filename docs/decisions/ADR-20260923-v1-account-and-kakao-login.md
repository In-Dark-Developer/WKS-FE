# ADR-20260923: V1 은 카카오 로그인 쿠키 세션을 더하고, 기록의 출처를 게스트 브라우저와 계정 둘로 둔다

- Status: Accepted
- Date: 2026-09-23
- Deciders: @jjjung0921 (제안) / 리뷰어는 PR 승인자

## Context

V1 기획 개정(2026-09-22)이 FR-19~FR-31 을 더했다. 그중 FR-20(카카오 로그인)·FR-21(계정 기록 복원)과
NFR-7(JWT 를 쿠키로, 만료 15일, CORS 자격 증명 허용)·NFR-8(인앱 브라우저에서도 로그인 완주)이
이 저장소의 세션 설계를 직접 건드린다.

지금 설계는 ADR-20260914-result-ownership-in-browser 다. 백엔드가 인증을 두지 않기로 해서,
'내 결과'는 이 브라우저가 `POST /results` 로 만든 `resultId` 하나이고 `src/api/session.ts` 만
localStorage 를 읽고 쓰며, 보호 화면은 `requireSession` 가드가 그 값으로 판단한다.

그 설계가 남긴 구멍이 V1 의 출발점이다 — 기기를 바꾸거나 브라우저 데이터를 지우면 궁합 지도를 잃는다(US-7).
ADR-20260914 는 이것을 "감수한 것"으로 적었고, V1 은 이것을 고치기로 했다.

제약은 다음과 같다.

- 사주 보기·결과 조회·공유·친구 궁합은 **로그인 없이 끝까지 동작해야 한다**(FR-20). 로그인은 궁합지도
  저장·복원과 소개팅에만 필요하다.
- JWT 는 `HttpOnly` 쿠키로 온다(NFR-7). 프론트엔드는 쿠키 값을 읽을 수 없다.
- 카카오톡·인스타그램 인앱 브라우저는 유입의 24% 이고 저장소·쿠키가 기본 브라우저와 따로다(NFR-8).
  `src/main.tsx` 는 이미 인앱을 기본 브라우저로 넘긴다.
- V1 API 계약은 아직 `docs/api/openapi.yaml` 에 없다. 로그인 콜백·계정-결과 연결·궁합 이유는
  2026-09-22 BE 회의록 기준이며 계약 갱신이 Phase 09/T2 착수의 전제다.

## Problem

로그인이 들어오면 '내 기록'의 출처가 둘이 된다 — 이 브라우저의 `resultId` 와 계정.
(1) 로그인 여부를 무엇으로 판단하고, (2) 두 출처가 모두 있을 때 무엇을 보여주며,
(3) 보호 화면의 가드를 어떻게 나누는가.

## Alternatives

1. **`me.ts` 단일 출처 + 게스트 `session.ts` 유지, 가드 3종으로 분리** — 로그인 여부는 `GET /me`
   응답으로만 판단하고, 비로그인 경로는 지금의 `resultId` 보관을 그대로 쓴다. 가드를 `requireSaju`(사주
   기록 필요)·`requireAuth`(로그인 필요)·`requireDatingProfile`(프로필 등록 필요)로 나눈다.
   비로그인 흐름이 하나도 바뀌지 않는다. 대신 화면마다 어느 출처를 보는지 정해야 한다.
2. **로그인을 전제로 통일하고 게스트 보관을 없앤다** — 출처가 하나라 단순하다. FR-20 의 "로그인 없이
   끝까지"를 위반하고, 사주 → 공유 → 궁합의 전환율(유입의 대부분이 공유 링크다)을 로그인 벽으로 깎는다.
3. **쿠키 존재 여부를 프론트가 직접 확인한다** — 요청 한 번을 아낀다. `HttpOnly` 라 읽을 수 없고,
   인앱에서 쿠키가 막히는 경우를 '로그인됨'으로 잘못 읽는다.

## Decision

대안 1.

- **로그인 판단은 `src/api/me.ts` 하나다.** 쿠키를 직접 읽지 않고 `GET /me` 응답(계정·프로필 유무)으로만
  판단한다. 쿠키가 막힌 인앱과 비로그인이 같은 경로로 처리된다.
- **게스트 기록은 그대로다.** `src/api/session.ts` 의 키 `wks:session`·값 `{ v: 2, resultId }`·
  함수 이름을 유지한다. ADR-20260914 의 비로그인 경로는 바뀌지 않는다.
- **두 출처가 모두 있으면 계정이 이긴다**(FR-21). 계정에 기록이 있으면 브라우저 기록은 연결하지 않고
  그대로 둔다. 계정이 비어 있을 때만 현재 브라우저의 `resultId` 를 계정에 연결한다. 로그인을 취소하거나
  실패해도 현재 지도와 비로그인 기록은 남는다.
- **가드는 `src/app/routes/guards.ts` 가 세 개를 갖는다** — `requireSaju`(쓸 수 있는 사주 기록이
  없으면 사주 입력으로), `requireAuth`(비로그인이면 소개팅 인트로로), `requireDatingProfile`(프로필이
  없으면 프로필 등록으로). 기존 `requireSession` 은 `requireSaju` 가 이어받는다.
- **`src/api/client.ts` 는 `credentials: 'include'` 로 보내고 401 을 로그아웃 상태로 다룬다.**
  인증 헤더는 계속 싣지 않는다.
- 적용 범위는 Phase 09~11 이다. 계약이 확정되기 전에는 `api/` 의 함수 시그니처만 두고 화면을 진행한다.

## Rationale

- 결정적 기준은 FR-20 의 "사주 보기·공유·친구 궁합은 로그인 없이 끝까지"다. 대안 2 는 이 줄을 위반한다.
- `HttpOnly` 와 NFR-8 이 대안 3 을 뺀다. 쿠키를 못 읽는 것과 쿠키가 막힌 것을 구분할 방법이 프론트에 없고,
  구분하지 못한 채 '로그인됨'으로 판단하면 인앱 사용자가 빈 화면을 본다. `GET /me` 는 두 경우를 같은
  응답으로 만든다.
- 두 출처의 우선순위를 `me.ts` 한 곳에서만 판단하게 해야 화면마다 규칙이 갈라지지 않는다.
  ADR-20260913 이 "요청/캐시 라이브러리를 두지 않고 loader 가 읽는다"로 정한 구조와 같은 이유다.
- 가드를 셋으로 나누는 이유는 진입 조건이 실제로 세 종류이기 때문이다 — 사주 기록, 로그인, 프로필.
  하나의 가드에 조건을 얹으면 리다이렉트 목적지가 화면마다 달라 조건문이 가드 안에 쌓인다.

## Consequences

- 긍정: 기기를 바꿔도 궁합 지도가 복원된다(US-7, SC-7). 비로그인 유입 경로(공유 링크)는 로그인 벽 없이
  그대로 동작한다. 로그인 판단이 한 파일에 모여 인앱 쿠키 차단이 특수 분기가 되지 않는다.
- 부정 / 감수한 것:
  - 보호 화면마다 `GET /me` 왕복이 는다. loader 안에서 부르고 캐시 계층은 두지 않는다(ADR-20260913).
  - 계정이 이미 차 있으면 로그인 직전 브라우저에서 만든 결과는 계정에 들어가지 않는다 — FR-21 이 정한
    동작이고, 두 기록을 합치는 규칙은 두지 않는다.
  - 쿠키가 막힌 인앱 사용자는 로그인하지 않은 것과 같이 다뤄진다. `src/main.tsx` 의 기본 브라우저 전환이
    이 경우를 줄이지만 없애지는 못한다.
  - V1 계약이 확정되기 전에 쓰는 `api/` 파일은 시그니처만 맞고 경로·스키마는 비어 있다.
- 후속 작업:

    Persistence · Cross-cutting Concerns (이 PR)
  - 공지 `2026-09-23-v1-architecture` (이 PR)
  - `docs/api/openapi.yaml` — 로그인 콜백 · `GET /me` · 계정-결과 연결 (Phase 09/T2, 백엔드 계약 선행)
  - Phase 09 T2·T3 — `src/features/auth/`, `src/api/me.ts`, 가드 3종의 구현과 테스트
  - ADR-20260914-result-ownership-in-browser 는 비로그인 경로의 근거로 계속 유효하다. 이 ADR 은 그것을
    뒤집지 않고 로그인 경로를 더한다.
