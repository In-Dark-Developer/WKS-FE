# ADR-20260914: 인연카드 이미지를 `html-to-image` 로 만든다

- Status: Accepted
- Date: 2026-09-14
- Deciders: @gn00py48 (제안) / 리뷰어는 PR 승인자

## Context

FR-5 는 인연카드를 이미지로 만들어 인스타 스토리로 공유하게 한다. 카드 화면(`src/ui/DestinyCard.tsx` · `DestinyCard.css`, 04/T2 의 `ConnectionCard`)은 이미 있고, 남은 것은 그 DOM 을 PNG 로 바꾸는 일이다 (Phase 04 T4).

카드는 단순한 사각형이 아니다. 컨테이너 쿼리(`container-type: inline-size` 와 `calc(100cqw / 323)`), `aspect-ratio`, `color-mix()`, webp·svg 배경 두 장 겹치기, 절대 배치된 십이간지 캐릭터 12종, 등급 스탬프 SVG, 그리고 커스텀 폰트 3종(Pretendard 가변 dynamic subset · 동국체 434KB · 성곡체 205KB)을 쓴다.

제약은 두 가지다. NFR-2 의 초기 JS 250KB gzip 예산(현재 147KB)과, MVP 마감 2026-09-17.

## Problem

브라우저에서 카드 DOM 을 어떤 방법으로 PNG `Blob` 으로 만들 것인가. 그리고 그 방법이 의존성 추가를 요구한다면 무엇을 받아들일 것인가.

## Alternatives

1. **`html-to-image`** (MIT, 1.11.13, unpacked 315KB) — DOM 을 SVG `foreignObject` 에 넣고 `<img>` 로 그려 캔버스에 옮긴다. 장점: 그리는 주체가 **브라우저 자신**이라 컨테이너 쿼리·`color-mix`·`aspect-ratio` 가 그대로 나온다. 작고 API 가 `toBlob` 하나다. 단점: 외부 리소스를 전부 data URL 로 인라인해야 해서 폰트가 무거우면 느리다. jsdom 에서 결과를 검증할 수 없다.
2. **`html2canvas`** (MIT, unpacked 3.4MB) — CSS 를 **다시 해석해** 캔버스에 직접 그린다. 장점: 폰트 인라인이 필요 없다. 단점: 렌더러를 재구현한 것이라 지원 목록에 없는 CSS 는 조용히 무시된다 — 컨테이너 쿼리·`color-mix` 가 그 목록에 없다. 카드가 어긋나게 나온다. 크기도 10배다.
3. **캔버스에 직접 그리기** (의존성 0) — `canvas` API 로 배경·캐릭터·텍스트·스탬프를 좌표로 찍는다. 장점: 의존성이 없고 결과가 결정적이며 테스트가 쉽다. 단점: `DestinyCard.css` 의 레이아웃(캐릭터 12종 좌표, 등급 줄, 줄바꿈, 폰트 메트릭)을 **통째로 다시 구현**해야 하고, 디자인이 바뀔 때마다 두 곳을 고쳐야 한다. 마감 3일 안에 할 수 있는 크기가 아니다.
4. **백엔드 렌더** — 서버가 결과 id 로 카드 PNG 를 만들어 준다. 장점: 클라이언트가 가볍고 OG 썸네일(NFR-3)과 재료를 공유한다. 단점: 이 저장소는 프론트 전용이고 계약에 그런 엔드포인트가 없다(PRD Q3). 마감 전 합의·구현이 불가능하다.

## Decision

**1번 `html-to-image` 를 채택한다.**

- `src/lib/cardImage.ts` 가 유일한 사용처다. 화면은 `renderCardImage(card)` 만 부르고 라이브러리를 모른다.
- 라이브러리는 **동적 import**(`await import('html-to-image')`)로 별도 청크에 둔다 — 공유를 누른 사람만 받는다.
- 화면 밖에 인스타 스토리 규격(1080×1920) 프레임을 만들어 카드 **사본**을 가운데 놓고 그 프레임을 찍는다. 사용자가 보고 있는 카드는 건드리지 않는다.

## Rationale

결정적인 기준은 **CSS 재현도**였다. 카드 레이아웃이 컨테이너 쿼리 위에 서 있어서, CSS 를 재해석하는 2번은 지금 디자인을 그대로 낼 수 없다. 1번은 브라우저에게 그리게 하므로 화면에 보이는 것이 곧 결과다.

3번은 의존성이 없다는 점에서 가장 깨끗하지만, 레이아웃을 두 번 관리하게 만든다 — 디자인이 아직 움직이는 중(인연카드 등급 표기가 2026-09-13 에 바뀌었다)이라 특히 나쁘다.

번들 예산은 동적 import 로 피했다. 실제로 재 보니 라이브러리가 **별도 청크 gzip 5.10KB** 로 갈라져 나가고 초기 JS 는 147.2KB 그대로였다(`pnpm build`, 2026-09-14). NFR-2 의 250KB 예산에 영향이 없다.

## Consequences

- 긍정: 화면 코드를 고치지 않고 이미지가 나온다. 디자인이 바뀌어도 이미지가 따라온다. 초기 번들이 늘지 않는다(별도 청크 gzip 5.10KB). 라이브러리 교체 지점이 `src/lib/cardImage.ts` 한 곳이다.
- 부정 / 감수한 것:
  - 런타임 의존성이 하나 늘었다 (ADR-20260911 의 '도입 금지' 목록에는 없는 순수 유틸이지만, 추가는 이 ADR 로 승인받는다).
  - **폰트 인라인 비용** — 라이브러리가 문서의 `@font-face` 를 전부 data URL 로 만든다. 동국체 434KB·성곡체 205KB 에 Pretendard dynamic subset(여러 조각)까지 더해지면 첫 생성이 느릴 수 있다. 실제 소요 시간은 04/T5 에서 실기기로 재고, 넘치면 카드가 쓰는 폰트만 담은 `fontEmbedCSS` 를 넘기는 방식으로 좁힌다.
  - **jsdom 에서 결과를 검증할 수 없다.** `foreignObject` 렌더와 캔버스가 없어 단위 테스트는 프레임 조립·정리·실패 처리까지만 본다. 그림 자체는 `/preview/card` 와 실기기 확인이 유일한 관문이다 (Phase 04 Validation Plan).
- 후속 작업: 04/T5 가 `renderCardImage` 를 Web Share(파일)·저장 폴백에 잇고 실기기에서 소요 시간·글꼴 누락을 확인한다. 넘치면 이 ADR 에 후속 ADR 로 폰트 범위를 좁힌다.
