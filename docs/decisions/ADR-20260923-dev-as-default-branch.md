# ADR-20260923: `dev` 를 기본·통합 브랜치로, `main` 을 운영 배포 브랜치로 둔다

- Status: Accepted
- Date: 2026-09-23
- Deciders: @jjjung0921

## Context

`main` 병합이 곧 운영 배포다(ADR-20260922-netlify-org-repo-direct). V0.5 가 축제 전까지 운영되는 동안
V1(카카오 로그인 · 소개팅 · 재화)을 만들기 시작했고, 스트림이 하나씩 `main` 에 들어갈 때마다 운영 화면이
바뀐다. 백엔드는 같은 이유로 운영(`api.`)과 개발(`dev.threadoffate.site`) 서버를 분리했다(09/22 회의 §3-G).
프론트에는 이미 `dev` 브랜치가 있고 그 브랜치 배포는 검색엔진에서 빠지지만(8d24c72), 스트림은 여전히
`main` 에서 갈라져 `main` 으로 돌아온다.

## Problem

작업을 모으는 브랜치와 운영에 나가는 브랜치를 나눌 것인가. 나눈다면 도구·보호 규칙·문서의 `main` 가정을
어떻게 함께 옮길 것인가.

## Alternatives

1. 지금처럼 `main` 하나 — 흐름이 단순하고 도구를 안 건드린다 / 스트림 병합이 곧 운영 배포라 축제 기간에
   V1 작업을 병합할 수 없다. 병합을 미루면 스트림이 길어지고 충돌이 커진다.
2. `dev` 를 기본 브랜치로, `main` 을 배포 브랜치로 — 스트림은 `dev` 로 모이고 운영 배포는 릴리스 PR 이
   일으킨다 / 브랜치가 둘이라 동기화 부담이 생기고, `main` 가정이 박힌 도구·규칙을 함께 옮겨야 한다.
3. 릴리스 브랜치를 따로 판다(`release/*`) — 배포 단위를 명시할 수 있다 / 6일 남은 일정에 비해 절차가 무겁다.

## Decision

2안. 기본 브랜치는 `dev`, 운영 배포 브랜치는 `main` 이다.

- 스트림 `ws/<id>` 는 `dev` 에서 갈라져 `dev` 로 PR 한다. 동기화는 `git merge dev`.
- 운영 배포는 `dev` → `main` 릴리스 PR 병합이다. Netlify 는 그대로 `main` 을 빌드한다.
- 보호 규칙은 두 벌이다: 기존 `main protection` 룰셋은 `~DEFAULT_BRANCH` 를 대상으로 하므로 기본 브랜치를
  바꾸면 자동으로 `dev` 를 보호한다. **운영 브랜치가 무보호로 남지 않도록 `main` 전용 룰셋을 먼저 만든다**
  (`ai-check` · `commands` 필수, 승인 1건, merge commit 만 허용).
- 도구는 통합 브랜치를 한 곳에서 정한다: `scripts/lib/common.sh` 의 `INTEG_BRANCH`(기본 `dev`,
  `AI_INTEG_BRANCH` 로 덮어쓰기) 와 `integ_ref()`. 이전 이름 `main_ref()` 는 없앴다.

## Rationale

- 축제(2026-09-29)까지 V0.5 를 운영하면서 V1 을 만든다. 병합을 막지 않으면서 운영을 지키는 방법은 두 브랜치뿐이다.
- 도구가 `main` 을 참조하는 지점은 `main_ref()` 하나로 모여 있었다 — 이름만 바꾸면 스트림 열기·`gc`·
  `--ready` 의 base 판정이 한 번에 따라온다. 전환 비용이 작다.
- 3안의 릴리스 브랜치는 배포가 잦지 않은 지금 절차만 늘린다. 필요해지면 `main` 앞에 덧붙이면 된다.

## Consequences

- 긍정: 스트림을 계속 병합해도 운영이 흔들리지 않는다. 릴리스 시점이 PR 하나로 드러난다.
- 부정 / 감수한 것: 브랜치가 둘이라 `dev` → `main` 을 누가 언제 올리는지 정해야 한다(당분간 Lead).
  전환 시점에 열려 있던 PR 들은 base 가 `main` 이라 그대로 병합한 뒤 다음 PR 부터 `dev` 를 쓴다.
- 후속 작업: GitHub 설정 두 가지 — ① `main` 전용 룰셋 생성 ② 기본 브랜치를 `dev` 로 변경. 이 PR 은 저장소
  안의 도구·문서만 옮긴다(설정은 저장소 관리자 권한이 필요하다).
