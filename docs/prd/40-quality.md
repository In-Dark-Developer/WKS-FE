## Non-functional Requirements

`담당` 열은 Notion ⚔️ PRD 보드 `담당자` 의 사본이다 — 원본은 보드이고 동기화가 읽지도 쓰지도 않으니
배정이 바뀌면 보드를 먼저 고친다. 이미 충족한 NFR 과 미배정은 `—` 로 둔다.

| ID    | Requirement                                              | Target                                                        | 확인 방법 | 담당 |
|-------|----------------------------------------------------------|---------------------------------------------------------------|-----------|------|
| NFR-1 | 모바일 우선 — 축제 현장에서 휴대폰으로 쓴다              | 360–430px 폭 기준 설계, 데스크톱은 중앙 정렬 폴백             | 360·390·430px에서 가로 스크롤 0 | 이정진 |
| NFR-2 | 첫 화면 체감 속도                                        | 4G 환경에서 LCP < 2.5s, 초기 JS 전송량 < 250KB(gzip)          | 측정 도구는 Phase 08에서 정한다 | 이정진 |
| NFR-3 | 공유 링크 미리보기                                       | 카카오·인스타·메신저에서 제목·설명·썸네일이 보인다            | 각 앱에 링크 붙여넣기. SPA라 동적 OG는 백엔드 협의 | 이정진 |
| NFR-4 | 개인정보                                                 | 추가 정보는 동의 이후에만 전송, 연락처(전화번호·인스타그램 아이디)는 매칭 성립 전 비노출 | 미성립 상태에서 화면·네트워크 응답에 연락처 없음 | 이동건 |
| NFR-5 | 접근성 기본                                              | 모든 입력에 라벨, 본문 대비 4.5:1 이상, 키보드로 폼 완주 가능 | 키보드 수동 조작 + `getByRole` 라벨 테스트 | 이정진 |
| NFR-6 | 브라우저 지원                                            | iOS Safari·Android Chrome 최신 2개 메이저                     | 실기기 각 1대에서 전체 흐름 | 이정진 |
| NFR-7 | 인증 방식                                                | JWT 를 쿠키로 전달하고 만료는 15일. CORS 는 자격 증명 허용이 필요하다 | 로그인 후 새로고침·재방문에 세션이 유지된다 | 곽도윤 |
| NFR-8 | 인앱 브라우저                                            | 카카오톡·인스타그램 인앱에서 로그인과 세션 유지가 동작한다 (유입의 24%) | 두 인앱에서 로그인 → 궁합지도 저장까지 완주 | 이정진 |
| NFR-9 | 해설·궁합 이유 생성 비용                                 | 사주 해설은 결과 생성 시 1회, 궁합 이유는 최초 열람 시 1회 생성하고 이후 저장값을 쓴다 | 같은 결과·같은 쌍을 다시 열 때 생성이 일어나지 않는다 | — |
| NFR-10 | 운영·개발 분리                                          | 운영(api)과 개발(dev) 서버가 DB·계정·LLM 키·Redirect URI·CORS 를 공유하지 않는다 | dev 에서 만든 데이터가 운영 조회에 나타나지 않는다 | — |


## Success Criteria

각 항목은 실기기(iOS Safari · Android Chrome) 한 대씩에서 아래 절차대로 확인한다. 수치 목표의 측정 도구는 Phase 08에서 정한다.

| ID  | 기준                                                                                      | 확인 방법 |
|-----|-------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------|
| SC-1 | 사주 입력 → 결과 → 인연카드 공유까지 한 번에 끝난다 (G1)                                   | 새 브라우저 프로필로 시작해 끝까지 진행. 막히는 화면 0개, 공유 시트 또는 이미지 저장이 실제로 열린다 |
| SC-2 | 입력 시작부터 결과 화면까지 30초 안에 끝난다 (G1)                                          | 위 절차를 스톱워치로 3회 측정, 중앙값 ≤ 30초 (백엔드 응답 시간 포함)                                |
| SC-3 | 공유 링크 유입자가 사주를 입력하면 양쪽 궁합 지도에 점수와 등급이 나타난다 (G2)             | 기기 두 대로 링크 공유 → 입력 → 두 지도 모두에서 같은 등급이 보인다                                 |
| SC-4 | 사전신청 모달에서 정보 입력과 동의를 마치면 완료 상태가 보이고 상대 정보 열람권을 얻는다. 소개팅 후보 화면은 축제 당일부터 열린다 (G3) | 동의 없이 제출 시 전송되지 않고, 동의 후 제출 시 "신청이 완료되었습니다"가 보인다                    |
| SC-5 | 연락처(전화번호·인스타그램 아이디)는 양측 운명의 실이 성립한 경우에만 보인다 (G4)          | 미성립 상태에서 화면·네트워크 응답 어디에도 연락처가 없다. 성립 후에만 나타난다                     |
| SC-6 | 공유 링크가 카카오·인스타·메신저에서 제목·설명·썸네일과 함께 보인다 (NFR-3)                | 각 앱에 링크를 붙여넣어 미리보기 확인                                                               |
| SC-7 | 로그인하면 다른 기기·브라우저에서도 내 궁합지도가 복원된다 (G6) | 기기 A 에서 궁합 3건을 만들고 로그인 → 기기 B 에서 로그인 시 같은 지도가 보인다 |
| SC-8 | 소개팅에서 실을 써서 정보를 열고 운명의 실을 보낼 수 있다 (G7) | 프로필 등록 → Top 3 노출 → 항목 1개 해금(잔액 차감 확인) → 전송 → 요청함 '보낸 신청'에 뜬다 |
| SC-9 | 받은 요청을 수락하면 양쪽에 연락처가 공개된다 (G7) | 계정 두 개로 요청 → 수락 → 양쪽 화면·응답에 연락처가 나타난다. 거절 시에는 나타나지 않는다 |
